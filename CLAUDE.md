## Project

Book Exchange: an Expo/React Native app backed by a local Express API and PostgreSQL. The mobile bundle holds no database credentials and never talks to Postgres directly — Expo only talks to the local API at `EXPO_PUBLIC_API_URL`.

## Commands

```bash
npm run dev:all          # API (server/src/index.ts via tsx watch) + Expo, together
npm run dev:api          # API only
npx expo start --ios     # app only, in a second terminal, once the API is running

npm run db:setup         # creates book_exchange_local, applies server/db/schema.sql, seeds data, writes .env.local
CONFIRM_DB_RESET=book_exchange_local npm run db:reset   # gated destructive reset; re-run db:setup after

npm run typecheck        # tsc --noEmit
npm run lint             # expo lint
npm run check            # typecheck + lint
npm run test:server      # tsx --test server/test/**/*.test.ts (spins up book_exchange_test DB, see server/test/setup.ts)
npm run build:web        # expo export --platform web

curl http://127.0.0.1:4000/health   # verify the API + DB connection
```

Run a single server test with `tsx --test server/test/api.test.ts` (or `--test-name-pattern` for one case). There is no client-side test suite currently.

Requires PostgreSQL 17 running locally (`brew services start postgresql@17`) and Node 20+.

## Architecture

```
app/                              Expo Router screens/navigation (route files only)
src/
  domain/                         Framework-independent domain models
  application/services/           Use-case and application services
  infrastructure/local-api/       HTTP client, auth/session, secure storage, realtime adapter
  presentation/
    components/                   Shared visual components
    hooks/                        Presentation-facing hooks
    providers/                    App-wide React state (AuthProvider, CartProvider, ...)
    theme/                        Semantic design tokens
  shared/config/                  Runtime/integration config (environment.ts, stripe-products.ts)
server/
  db/                             schema.sql + seed.sql for local Postgres
  scripts/                        setup-db.ts / reset-db.ts (safe, gated automation)
  src/                            Express API: app.ts, auth.ts, data-router.ts, rpc-router.ts, realtime.ts, db.ts
  test/                           node:test + supertest integration tests against book_exchange_test DB
```

**Dependency direction:** routes (`app/`) use presentation components/hooks and application services → application services use domain models and the infrastructure interface → infrastructure owns network/persistence details. `server/` is a separate process and never imports mobile presentation code.

**Runtime boundaries:**
- Express (`server/src/app.ts`) authenticates requests, validates allowed resources/fields, and owns all DB access.
- `server/src/data-router.ts` is a generic REST-ish layer over Postgres tables, gated per-table by a `tableDefinitions` map (`readable` / `privateReadable` / `writable` / `publicRead` columns) — extend this map rather than bypassing it when exposing new fields.
- `server/src/rpc-router.ts` handles named RPC-style operations (follow counts, recent chats, etc.) that don't fit the generic table CRUD shape.
- Google Books and Stripe secrets are read only by the server; never prefix secrets with `EXPO_PUBLIC_`.
- WebSocket events (`server/src/realtime.ts`) containing private records are filtered to their owners/conversation participants.

**Migration adapter:** `src/infrastructure/local-api/client.ts` (`dataClient`) is a fluent query client that mimics a hosted-backend SDK, used to move existing screens off a former hosted backend without a risky rewrite. New features should prefer focused, typed application services/repositories over adding more generic `dataClient` queries to screens.

**Next structural milestone (per ARCHITECTURE.md):** `browse`, `add`, `chat`, and `profile` routes are still large monoliths; the intended pattern going forward is `src/features/<feature>/{application,domain,infrastructure,presentation}` with route files limited to navigation params and screen composition.

## Environment

- `.env.local` is git-ignored and generated by `npm run db:setup` with a random `JWT_SECRET`; don't hand-edit unless adding an integration key.
- Physical devices need `EXPO_PUBLIC_API_URL` set to the dev machine's LAN address; Android emulator auto-uses `http://10.0.2.2:4000`.
- See `.env.example` for the full variable list.

Dev login seeded by `db:setup`: `demo@bookexchange.local` / `DemoPass123!`.

## Graphify Knowledge Graph Workflow

This project has an existing Graphify knowledge graph located at:

- `graphify-out/graph.json` — machine-readable knowledge graph
- `graphify-out/GRAPH_REPORT.md` — high-level architecture overview
- `graphify-out/graph.html` — visual graph for humans

### Required workflow

For tasks involving architecture, codebase navigation, dependencies, execution flow, data flow, impact analysis, or locating implementations:

1. Query Graphify before searching or reading repository files.
2. Prefer Graphify MCP tools when available:

   - `graph_stats`
   - `query_graph`
   - `get_node`
   - `get_neighbors`
   - `shortest_path`
   - `get_community`
3. When MCP tools are unavailable, run:

   - `graphify query "<question>"`
   - `graphify explain "<symbol-or-component>"`
   - `graphify path "<source>" "<target>"`
4. Use `GRAPH_REPORT.md` only for initial high-level orientation.
5. Do not read or parse `graphify-out/graph.json` directly unless Graphify tooling is unavailable.
6. Do not begin with repository-wide `Glob`, `Grep`, `find`, `rg`, or broad file exploration.
7. Use Graphify results to identify the relevant symbols and source locations.
8. After Graphify identifies the relevant locations, read only the specific source files needed to verify details or implement changes.
9. Before completing architecture or impact-analysis tasks, state which Graphify queries or tools were used.

### Keeping the graph current

When the codebase has changed since the graph was generated, update it before relying on its results:

```bash
graphify update .
```

When a full regeneration is required, use the installed Graphify skill:

```text
/graphify .
```
